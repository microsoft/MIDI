8. The connection monitor window. Compact, because there will often be two or three open next to the canvas. It reads the same as the Windows MIDI Monitor: the same words, the same message names and colors, and the same description of each message, from code the two apps share.

1 2 3 4 5
  1. Title: the window's number and color (matching the dot on the connection), then "From → To". In Alt+Tab it reads "Impact LX Mini → Message type filter – Studio Rig".
  2. From and To spell out the connection, groups included, using the names on the canvas. A rename on the canvas updates it. On the right: Routing, Not routing, Muted or Removed.
  3. Pause, Clear, Clock, Active Sensing. Pause stops adding rows but keeps counting, so you can read without the list moving. Clear asks nothing: this list is short-lived. Clock and Active Sensing start hidden, as in the Monitor, because a clock on a connection drowns everything else. The count on the right includes hidden and dropped messages.
  4. Time, Message, Details. Time is the message's own timestamp, in milliseconds since the window opened, so a message scheduled for later shows when it will play. Message is the UMP words and the message name chiclet. Details is the Monitor's description: note names, velocities, controller names, tempo and so on. Right-click a row to copy it, the same choices as the Monitor. The window keeps the last 5,000 messages.
  5. Always on top is on by default for these windows, so they don't fall behind the editor the moment you click the canvas. Minimize and close only: no maximize, it isn't that kind of window.

States

Testing. Messages from Test (the patch's trace) show here too, marked Test, even when the patch isn't routing. Nothing is sent to a device by a test, so the tag keeps the two apart.
Nothing yet. Says how to get messages here, instead of an empty table.
Removed. The window stays with what it captured, and says why nothing new arrives. Undo brings the connection back, and the window picks up where it left off.

How it would work

  1. No cost when nobody watches. Routing runs on the service's callback thread with no locks and no allocation, and that has to stay true. Each connection gets a slot for a watcher. When the slot is empty, the cost is one check. When a window is watching, the message is copied into a fixed-size buffer and the window collects it about 20 times a second. If the window falls behind, the oldest copies are dropped and counted ("12 dropped"); routing never waits for a window.
  2. Test feeds the same windows. The patch trace already knows which connections each test message went along, so it hands those messages to any window watching those connections, marked as Test.
  3. Shared description code. The Monitor's message describer moves to the code the tools already share, and both apps use it. It would take plain UMP words instead of a Monitor row, and the label words ("Note", "Velocity", "Controller"...) stay in each app's own string resources, as the repository requires, with the Patchbay getting a copy of the Monitor's. The Patchbay's own short descriptions for the trace stay as they are.
  4. Windows belong to their patch's editor. Closing the editor closes its watch windows. A patch whose editor is closed but which keeps routing (routing runs from the tray too) has no watch windows. Watch windows aren't saved with the patch, so opening a patch never opens a stack of windows you'd forgotten about.
