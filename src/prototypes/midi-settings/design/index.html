Windows MIDI Settings, Configurations window comps

A window for everything people do with whole configurations: switch, back up, restore, share with another PC, and import. These are HTML: open any page in a browser, or run capture.ps1 for pictures in shots and check.ps1 for a layout check. They are pictures of the app, not the app. No product code has changed.

1. Opening the window
A Configurations button in the pinned group on the right of the toolbar, and a slimmer card in Global MIDI settings.
2. Configurations
The one in use and what's in it, the others on this PC, switching with a restart prompt, the ... menu, and the read-only state.
3. Backups
Every backup with the reason it exists, what's in the one you pick compared with now, Restore, and deleting old backups.
4. Share
One package file with pictures, for another PC. Works without administrator rights.
5. Import
Where a package comes in, with pointers for people who wanted Share or Backups.
6. What will happen
One line per item saying what will happen: device names added or replaced, loopback and host names that clash, a host named after the other PC, a transport that isn't installed, other settings.
7. Done
The result per item, a restart only when something needs one, and Undo this import.

How it would be built

  • An engine with no user interface, in its own folder of plain C++: no XAML, no app strings, no precompiled header from the app. It returns data and reason codes, and the window turns those into words. When MIDI Settings is redesigned for Windows, the new UI keeps the engine and replaces only the window.
    • ConfigLibrary: list, create, rename, duplicate, delete, and switch the configuration in use. Today's file functions in MidiConfig.cpp move here.
    • ConfigBackups: today's MidiConfigBackups.cpp, plus a reason in each backup's name and the delete-old-backups rule.
    • ConfigInventory: reads a configuration or a package into parts (device names, pictures, loopbacks, Network MIDI 2.0, RTP-MIDI, Bluetooth, other settings) with counts and items.
    • ConfigPackage: writes and reads .midiconfigpack with the shared ZipWriter and ZipReader in midi-app-shared, the same code Glass and Sequencer use. Inside: package.json (name, note, PC name, date, parts, port naming), the configuration, and pictures/.
    • ImportPlan: compares a package with this PC and decides each item's status, problem and default choice. It reads this PC through calls the API already has: GetEndpointCustomizations, GetSavedLoopbackEntries (both loopback kinds), GetSavedHosts and GetSavedClients (Network MIDI 2.0 and RTP-MIDI), GetSavedDevices (Bluetooth), and GetInstalledTransportPlugins.
    • ImportApply: backs up first, then applies each item with the existing config classes (endpoint customization, loopback, basic loopback, network host and client, RTP-MIDI host and client, Bluetooth connect, synth) through SaveUpdate and SendUpdate. Pictures go through EndpointImageAssets, which already reuses identical files and renames clashes. It returns one result per item. Undo restores the backup.
  • No new API. The only direct file access is what MIDI Settings already does as an in-box tool: listing configurations and backups, and reading the configuration inside a package. The engine files that do it carry the DO NOT COPY banner.
  • Tests: a TAEF project for the engine, like Patchbay's engine tests: package round trip, clash and rename rules, other-PC detection, and what a plain .midiconfig.json without pictures does.
  • Other-PC detection: a package says which PC made it. A plain file doesn't, so a host whose name or service name starts with another PC's name counts as named after another PC. New hosts are named after the PC by default (<PC name>_windows_midisrv), which is what makes this work.
  • To check before building: that SaveUpdate saves a section for a transport that isn't installed (the RTP-MIDI case), and which items need SendUpdate as well as SaveUpdate to work without a restart.

Questions for you

  1. Import live, or write the file and restart? The comps apply items through the running service, so most of an import works at once and Undo is a restore. Writing the file instead always needs a restart.
  2. Defaults when a package disagrees with this PC. The comps keep the customer's own device names, synthesizer sound and port names, and leave out a loopback or host whose name is taken unless its box is ticked. A host named after the other PC takes this PC's name, ticked by default. OK?
  3. File type and name. .midiconfigpack, like Glass's .midilayoutpack? And should the installer register it, so double-clicking a package opens Import?
  4. Port naming in packages. It lives in the registry, not in the configuration file. The comps carry it in the package as an "other setting". Keep it?
  5. Backup reasons ("Before importing from STUDIO-PC") need the reason in the backup's file name, next to the stamp. Daily backups from the API are recognized by their date-only stamp. OK?
  6. Global MIDI settings: OK to take Create, Back up now, Add and Restore out of the dialog, leaving the name of the one in use and Manage configurations?
